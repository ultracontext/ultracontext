title: 'CLI'
description: 'Version control for agent context, from your terminal'

The `uc` CLI is **local-first**: every command talks to a SQLite database at
`~/.ultracontext/uc.db`. No server and no API key are required to get started. Point
it at the hosted Context API with `--remote` whenever you want.

It manages **many contexts explicitly** — there is no default context. Every targeted
verb (`append`, `get`, `update`, `delete`) takes a context id, resolved in this order:

1. the explicit `<id>` argument, else
2. the `UC_CONTEXT` environment variable, else
3. a clear error (`no context — pass an id or set UC_CONTEXT`).

The CLI mirrors the SDK method names one-to-one: `create`, `append`, `get`, `update`,
`delete`.

<Info>New here? Start with the [Quickstart](/quickstart) for a 2-minute setup.</Info>

## Install

One install gives you both the `uc` binary and the [SDK](/sdk).

```bash bash
npm install -g ultracontext   # the `uc` CLI, globally
```

The binary is available as both `uc` and `ultracontext`.

## Get started

```bash bash
uc init                                       # set up the local SQLite store
id=$(uc context create)                               # create a context → prints its id
uc context append "$id" "remember: deploy uses Fly.io"    # append a message
uc context get "$id"                                  # read the context
uc context list                                       # list all contexts
```

`uc context create` prints the new context id to stdout (a bare id in human mode, so
`id=$(uc context create)` works in a shell). Every other targeted verb takes that id — or set
`UC_CONTEXT` once and drop it:

```bash bash
export UC_CONTEXT=$id
echo "another note" | uc context append    # body via stdin (id from UC_CONTEXT)
uc context get
```

## Context commands

### `uc context create`

Create a new context, or **fork/clone** from an existing one with `--from`. Prints the
new context id. `--meta key=val` (repeatable) tags the **context** itself.

| Flag | Description |
|------|-------------|
| `--from <id>` | Fork/clone from an existing context id |
| `--version <n>` | Fork at a specific version |
| `--at <index>` | Fork at a message index |
| `--before <timestamp>` | Fork at the version before a timestamp |
| `--meta <key=val>` | Attach context metadata (repeatable) |

```bash bash
uc context create                                     # new empty context
uc context create --meta user_id=u_123 --meta env=prod
uc context create --from ctx_abc123                   # full fork/clone
uc context create --from ctx_abc123 --at 5            # fork the first 6 messages
uc context create --from ctx_abc123 --version 2 --meta reason=rollback
```

<Info>Fork/clone is `uc context create --from <id>`, mirroring the SDK's `create({ from })` — there is no separate `fork` verb. The `--version` / `--at` / `--before` selectors require `--from`.</Info>

### `uc context append <id> [text]`

Append a message to context `<id>`. Reads the body from the positional `text`, piped
stdin, or a `--message <json>` object. `--meta key=val` (repeatable) tags the
**message** (and merges into a `--message` body).

| Flag | Description |
|------|-------------|
| `--role <role>` | Message role (e.g. `user`, `assistant`) |
| `--meta <key=val...>` | Message metadata pairs (repeatable) |
| `--message <json>` | Parse a raw JSON message object (`role` / `content` / `metadata`) |

```bash bash
uc context append ctx_abc123 "the API runs on port 8787" --role user
echo "piped note" | uc context append ctx_abc123
uc context append ctx_abc123 --message '{"role":"assistant","content":"done","metadata":{"task":"deploy"}}'
uc context append ctx_abc123 "tagged note" --meta source=cli

# with UC_CONTEXT set, the id is implied (body must come from stdin or --message)
UC_CONTEXT=ctx_abc123 uc context append --message '{"content":"another note"}'
```

<Info>`--json` is the **global** machine-output toggle, not a body source. Raw message objects go through `--message`.</Info>

### `uc context get <id>`

Read context `<id>`. Time-travel with the version selectors.

| Flag | Description |
|------|-------------|
| `--version <n>` | Read a specific version |
| `--at <index>` | Read at a message index |
| `--before <timestamp>` | Read the version before a timestamp |
| `--history` | Include the version history |

```bash bash
uc context get ctx_abc123
uc context get ctx_abc123 --history
uc context get ctx_abc123 --version 2
uc context get ctx_abc123 --at 5
```

### `uc context update <id>`

Update messages in context `<id>`. Target one message by id **or** index. `--meta`
attaches **version** metadata to the resulting update.

| Flag | Description |
|------|-------------|
| `--id <id>` | Target a message by id |
| `--index <n>` | Target a message by index |
| `--content <text>` | New message content |
| `--meta <key=val>` | Attach version metadata (repeatable) |

```bash bash
uc context update ctx_abc123 --index 0 --content "New system prompt"
uc context update ctx_abc123 --id msg_xyz --content "Fixed!" --meta reason=typo
```

### `uc context delete <id...>`

Delete the whole context `<id>` (`--permanent`) or specific messages (`--ids`). The
`--meta` flag attaches an **audit** record on a permanent delete, or **version**
metadata on a message delete.

Pass **multiple ids** to **batch-delete** whole contexts. A batch is always
permanent, so it requires `--permanent` (a bare multi-id delete errors), and
`--ids` is rejected as ambiguous. The batch emits a `{ results, deleted_count }`
envelope (one row per id, with an error reason on failures) and exits `0` only
when every id deleted — any failed row exits `1` while still printing the rows.

| Flag | Description |
|------|-------------|
| `--permanent` | Permanently delete the whole context (irreversible; required for a batch) |
| `--ids <ids...>` | Delete only these message indices/ids (single target only) |
| `--meta <key=val...>` | Metadata pairs — audit (permanent) or version (messages) |

```bash bash
uc context delete ctx_abc123 --permanent --meta reason="GDPR request"
uc context delete ctx_abc123 --ids 0 2 -1 --meta reason=cleanup
uc context delete ctx_abc123 ctx_def456 ctx_ghi789 --permanent   # batch permanent delete
```

### `uc context list`

List **all** contexts by default. Filters are optional and combinable — there is no
cwd default.

| Flag | Description |
|------|-------------|
| `--source <source>` | Filter by capture source |
| `--project_path <path>` | Filter by project path |
| `--limit <n>` | Max contexts to return |

```bash bash
uc context list
uc context list --limit 20
uc context list --source claude --project_path /Users/alice/Code/myapp
```

## Remote commands

A **remote** is your one central machine, configured once. It carries the
coordinates each primitive needs: an SSH target (for fs sync and the event
transport) and, optionally, an API coordinate (a base url plus a key, for
contexts and events over HTTP). `--remote` on any command routes it to this
remote.

```bash bash
uc remote set user@vps:/srv/uc --host-id laptop      # set the SSH side
uc remote set local --api https://api.example.com --key sk_x  # add the API side
uc remote show                                        # the configured remote (key never printed)
uc remote test                                        # reachability of each configured leg
uc remote clear                                       # drop the remote coords (sources kept)
```

| Subcommand | Description |
|-----------|-------------|
| `set <target>` | Set the remote coordinates. `target` is `local` \| `user@host[:root]`. `--root <path>` overrides the workspace root, `--host-id <id>` the derived host id, `--api <url>` / `--key <token>` set the API side |
| `show` | Show the configured remote (the API key is never printed — only whether one is set) |
| `test` | Test reachability of each configured leg (SSH via a login-shell `uc --version`, API via an HTTP GET) |
| `clear` | Drop the remote coordinates, leaving your synced sources intact |

## Sync commands

`uc sync` is fs-first orchestration over [Mutagen](https://mutagen.io). It mirrors
agent session files between machines so your context follows you. Requires the
`mutagen` binary on your `PATH` (`uc doctor` checks for it).

```bash bash
uc remote set user@vps:/home/alice/.ultracontext   # configure your central remote
uc sync source add claude ~/.claude/projects       # add a synced source
uc sync start                                       # start enabled sources
uc sync status                                      # show live sessions
uc sync list                                        # configured sources + state
uc sync stop                                        # pause enabled sources
```

The sync target is configured by [`uc remote set`](#remote-commands) — the one
central machine `uc` routes to. `uc sync` only reads it.

| Subcommand | Description |
|-----------|-------------|
| `source add <name> <path>` | Add or update a synced source (`--disabled` to add without starting) |
| `source list` | List configured sources |
| `source remove <name>` | Remove a source (`--purge-remote` also deletes its hub workspace dir — destructive) |
| `source enable <name>` / `source disable <name>` | Enable / disable a source and start / pause its session |
| `start` / `stop` | Start / pause sync for enabled sources |
| `status` | Show live sync session status |
| `list` | List configured sources with sync state |
| `reset` | Terminate owned sessions and restart enabled sources |

Sync respects `.ultracontextignore` files under `~/.ultracontext/ignores/` (a
global file plus per-source `<source>/` files); their patterns become Mutagen
`--ignore` flags. The global file is seeded with sensible defaults on first use.
See [Sync → Ignore files](/concepts/sync) for the full list.

## Serve command

`uc serve` self-hosts the [Context API](/api-reference/introduction) plus the
[events](/concepts/events) endpoints over your **local SQLite store** — the same
db the `uc` verbs use. It's a self-contained server in the CLI (no Postgres, no
separate deploy) that runs under both Node and the standalone binary. Run it on a
VPS, then point another machine's [remote](/concepts/remote) API leg at it.

```bash bash
uc serve                          # 127.0.0.1:8787 over ~/.ultracontext/uc.db
uc serve --host 0.0.0.0 --port 9000   # bind all interfaces on a custom port
```

| Flag | Description |
|------|-------------|
| `--port <n>` | Port to listen on (default `8787`) |
| `--host <addr>` | Address to bind (default `127.0.0.1`) |
| `--db <url>` | SQLite db url (default the CLI's local db) |
| `--no-auth` | Disable bearer auth — **localhost-only dev**, every request is open |

On first run it mints a bearer key bound to the CLI's `local` project and prints
it **once** to stderr — copy it into `uc remote set <target> --api <url> --key …`.
See [Self-hosting → `uc serve`](/guides/self-hosting#uc-serve-self-host-in-one-command)
for the full flow.

## Utility commands

### `uc init`

First-run onboarding. Interactive on a TTY; non-interactive with `--yes` (or when
piped). Optionally seed a hosted backend.

| Flag | Description |
|------|-------------|
| `--yes` | Accept defaults without prompting |
| `--remote <baseUrl>` | Seed a hosted backend base url |
| `--api-key <key>` | Seed a hosted backend api key |

### `uc doctor`

Diagnose the local environment: uc version, `~/.ultracontext` presence, local DB
reachability, `mutagen` availability, remote reachability (only when configured),
and the credential source.

### `uc update`

Self-update the CLI. The install method (npm / brew / curl) is auto-detected. Use
`--dry-run` to print the command without running it.

### `uc commands`

Print the command tree. With `--json` it emits the full, machine-readable tree —
the authoritative source of truth for agents introspecting the CLI.

```bash bash
uc commands --json
```

## Local vs remote

By default the CLI is local-only. It switches to the hosted Context API when:

- you pass `--remote` on any context command, **or**
- a base url **and** api key are configured (via `uc init` or env vars).

| Variable | Description |
|----------|-------------|
| `UC_API_URL` | Hosted API base url (overrides config) |
| `UC_API_KEY` | Hosted API key (overrides config) |
| `UC_DB_URL` | Local SQLite url (overrides `~/.ultracontext/uc.db`) |
| `UC_CONTEXT` | Default context id for targeted verbs (`append` / `get` / `update` / `delete`) |

```bash bash
uc context list --remote                          # one-off against the hosted API
UC_API_KEY=uc_live_... uc context append "$id" "synced note"
```

## Output

Every command is pipe-aware. With `--json` — or whenever stdout is not a TTY —
output is machine-readable JSON. Data goes to **stdout**; status, spinners, and
errors go to **stderr**. Exit code is `0` on success, `1` on error, `130` on user
cancel.
